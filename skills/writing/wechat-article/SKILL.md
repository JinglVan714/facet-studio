# 公众号文章

这篇文章的目的：让一个没看过原始内容的人，**快速、舒服地理解这件事**。

默认不是“摘要”，也不是“一个 hook 的展开”，而是 **video-equivalent understanding**：读完能说出这件事大致是什么、怎么运作/怎么做、关键例子、边界。

你可以重排、合并、拆分、删减、改写、统一说法；可以用自己的知识把内容讲得更清楚。但事实、数字、引语、例子、机制、因果只来自内容；不能加内容没有的具体事实、数字、画面、结论。

## 读者契约（写之前先定；开头输出）

不要假定一个具体人设。读者模型只来自三层：

1. **request 优先**：前端请求给了读者、目标、平台、长度、角度、必须包含/避免，就按 request。
2. **最小读者**：没给就用“聪明、好奇、没有这个话题先验知识的普通读者”；只有常识，不假设年龄、职业、性别、地域、收入。
3. **知识契约**：不问“他是谁”，只问：
   - 这篇文章假设读者已经知道什么？（prerequisite）
   - 哪些术语/概念必须在使用前落地？（must ground）
   - 哪些内容读者可以跳过？（can_skip）
   - 读者要解决/理解的一个问题是什么？（reader_goal）
   - 标题承诺什么？（title_promise）

内容信号只能来自内容本身（例如“新手教程”“在家做”），不要编造身份细节。

开头先用 HTML 注释输出读者契约（不进正文）：

`<!-- reader_contract: {"assumed_prerequisites":["..."],"must_ground":["..."],"reader_goal":"...","can_skip":["..."],"title_promise":"..."} -->`

`can_skip` 是硬切清单，不是备注：正文出现它，就删，或缩成一句“可跳过”；不改契约就不写。

## 写前：内容地图（不输出）

先想清楚，再动笔：

1. **一句话整体承诺**：读完你能______。
2. **3–6 步读者路径**：读者先要知道什么 → 遇到什么问题 → 为什么 → 怎么做 → 代价。不是视频的章节顺序。
3. **内容地图**：每一步放哪些事实/例子/图；哪些合并、拆分、调序、删；哪些是 prerequisite / must ground。
4. **每层一个组织维度**：阶段、肉类、概念或问题；同一层不能混。需要另一个维度就用表格或 H3。
5. **术语/数字预算**：只保留理解必需的；先中文后英文括号一次；实现细节 cut 或 footnote。
6. **图计划**：每张图回答哪个读者问题、看哪里、说明什么。
7. **开头框架**：这是什么、读完得到什么、整体路径。

文章是**新的组合**，不是原文的改写版；视频顺序不是文章顺序。

## 标题

标题 = **主题 + 整体收益/范围**；清楚第一，钩子第二。

- 必须包含读者在找的**主题/对象**（一个教程、一个工具、一个概念、一个方法），不能只给一个细节、内部数字或比喻。
- 3 秒陌生人测试：没读过内容的人，能不能说出“这篇讲什么、我为什么读”？
- 钩子是读者能理解的 payoff / question，不是正文才解释的内部数字，也不是只覆盖一个动作的窄机制。
- 标题承诺整体，不是摘要，也不是谜语；正文必须兑现。
- 句式示例（不是定稿）：
  - `[主题/对象]：从……到……的完整教程`
  - `[主题/对象] 是什么？……怎么选`
  - `[读者问题]？[整体收益/范围]`

## H2

- 每个 H2 是读者此刻的问题/决策，或一个带收益的判断/动作；不是内容章节/流程标签。
- H2 的顺序是读者的问题链：我想做什么 → 为什么现在的做法不对/结果为什么怪 → 真正的原因 → 我该怎么做 → 代价/边界。
- 只读 H2，论证线还在（电梯测试）；读完一个 H2，读者想知道下一节。
- H2 不能提前使用还没解释的结论、分数、阈值或内部指标；如果 H2 里有，前一节必须先把它落地。
- 同一层只能一个维度；需要另一个维度用表格或 H3。
- 最后一节不是“最后/总结/结语”。

## 开头

前三句给**框架**：这是什么、读完得到什么、整体路径。钩子放在框架里，不要用细节代替框架。

- 教程：先说“这是一份完整的……教程”，再说关键的三件事。
- 解释：先说“你想搞懂/想做什么”，再说反常识/问题。
- 产品：先说“它是什么、解决什么问题”。
- 不要上来就一个动作、一行代码、一个数字；读者还不知道你在干什么。
- 钩子不能建立在一个读者还看不懂的内部结果上；如果开头用失败/反常识，先用一句话补上理解它所需的最小前提（读者要做什么、系统给什么结果/分数），再抛失败。
- 不要写“代码里/程序里/实现里”；用“系统/页面/搜索”的读者语言。

## 正文结构

### 通用

- 每一节回答上一节留下的问题；删掉不服务 `reader_goal` 的段落。
- 一段一个意思；段落之间是推进，不是并列答案的拼接。
- 概念先落地再用；一个概念一次；中文为主，英文术语第一次出现加括号，之后统一用中文或统一用英文。
- **同一层 H2 只能一个维度**；需要另一个维度用表格或 H3。
- 最后一节不是“最后/总结/结语”，是判断/动作/边界/下一步。
- 可以重排、合并、拆分、删减、改写；不能加内容没有的事实、数字、引语、画面、机制、因果。

### 按内容类型选骨架

- **教程/操作**：整体 frame → 材料 → 阶段或肉类（选一个维度）→ 失败点 → 可简化。
  - 阶段式（共享流程默认）：准备 → 处理 → 执行 → 收尾；不同对象的差异用表格或 H3。
  - 按对象/类别式（差异大时）：对象 A 全流程 → 对象 B 全流程 → 对象 C 全流程；共享部分单独讲。
  - 同一层不能混“阶段”和“肉类”。
- **解释/科普**：目标 → 它做什么 → 怎么运作 → 直觉做法 → 为什么失败/反常识 → 真正原因 → 该怎么做 → 代价。
  - 一个概念一次；先现象后名字；术语在读者第一次需要时落地；实现细节不进主线。
- **产品/工具**：是什么 → 不是什么 → 怎么运作 → 选项/模式 → 该不该用。
- **观点/评论**：现象 → 常见解释 → 内容的不同角度 → 证据 → 反方/边界 → 判断。
- **故事/经验**：场景 → 转折 → 做法 → 结果 → 边界。
- **混合内容**：选一个主 `reader_goal`；其他内容做一小段、表格，或删。

## 术语：统一、少、先需求后名字

- 同一个东西全篇统一一个说法。可以把口语里的“一串数字/数字/维度”统一成“向量”，第一次出现用一句最小解释；之后不要再来回换说法。
- 同一个东西的两种叫法不要混用：第一次解释后统一；不要让读者以为是两个东西。
- 不要写“代码里/程序里/实现里”；用“系统/页面/搜索”的读者语言。
- 只保留理解必需的 3–5 个术语；标题/H2 不放术语。
- **实现细节能压就压**：模型组件名、接口名、文件名、端口、字节数、精度、函数名、代码变量名、硬件型号、安装步骤，压成一句功能描述（“把输入变成数字的那部分”“每个数字占固定空间”“处理完要重新归一”“模型跑在一台本地机器上”）；不写实现名。
- 超过 3–5 个术语就重新检查：哪些可以压成中文描述、哪些可以删；正文的主线必须不依赖实现名也能读懂。
- 中文为主；英文术语第一次出现加括号，之后不再中英混杂。
- 不要用另一个术语解释术语。
- 模型知识可以用来把口语/转写里的说法规范化、统一、简化；不能改变原意，不能加新事实/数字/机制。

## 数字：强数字、必要数字，宁少勿多

社媒读者对数字很敏感。数字不是“我读完了内容”的证明；数字多了、价值低，读者会反感。**宁可没有，也不要凑。**

### 每个数字必须能回答三个问题

1. **这是什么？**（单位、对象、范围）
2. **它说明什么？**（和读者的判断/行动有什么关系）
3. **为什么需要它？**（删掉它，读者会失去什么决定/理解？）

答不上来，就删；不要留一个“看起来很具体”的孤数。

### 什么数字才有资格进来

- **改变判断/行动**：一个阈值导致结果全被筛掉；两个参数各管什么；时间够与不够。
- **锚定规模**：一个具体的总量；前后对比；一个可感知的比例。
- **让对比具体**：只留支撑结论的 2–3 个对比数字，不要整串。
- **提供可检查的阈值/范围**：一个读者能对照的时间、温度或次数。
- **说明代价/取舍**：切到 256 省 2/3 空间，但 128 开始漏。

### 无效数字

- 内部实现：内部维度、字节数、精度、内部 ID，除非读者是 builder 且真的要用。
- 同量纲的一串（如连续评分）：压成范围/结论，不要逐个列。
- 读者不会用的精度：保留到读者能用的位数，不要给无意义的尾数。
- 内容没有、自己算出来的差值/百分比，除非是决策必需的换算。
- 表格已经列出的数字，正文再逐个复述。
- 为了显得专业、为了“完整”、为了证明读过内容而放的低价值数字。

### 选择规则

- 每节只留 1–3 个“承担判断”的数字；其余压成范围/结论。
- 表格可以放全量数字；正文只讲为什么、顺序、例外。
- 标题/H2 只放强数字/必要数字；实现数字放代码块/脚注或删。
- 社媒文章尤其要克制：能不用数字就不用；用就用一个读者能记住、能拿去做决定的。
- 写前先列“我要用哪几个数字、每个数字让读者做什么决定”；列不出来就不要写。

## 图

- 每张图/SVG 先问：读者看完能多知道什么？如果只是把正文抽象化一遍，或者画一个读者无法映射的隐喻，删。
- 真实图示在关键机制、步骤、对比、结果处用；caption 只写“看哪里 + 这说明什么”，不要用“如图所示”复述正文。
- 表格列数字；正文讲关系、原因、例外、顺序。正文不逐个复述表格。
- 概念图要标映射：左/右/上/下分别对应什么；没有映射的图不是图，是装饰。
- 代码截图/界面截图只在读者需要看它时用；否则删。

## 写完：陌生人通读（同一次调用内，最多一轮）

假装你是一个没读过内容、只看到这篇文章的读者，从头读一遍：

1. 我 3 秒知道这篇讲什么吗？标题有没有“主题 + 整体收益”？
2. 开头有没有给框架，还是上来一个细节？有没有用一个还没解释的分数/阈值/内部结果当钩子？
3. 我在哪一句/哪一段卡住、要回读？哪一段想跳过？
4. 哪个数字我说不出“这是什么、它说明什么、为什么需要”？哪个数字只是噪音/低价值？
5. 哪个术语出现时我还没有需求？有没有中英混杂/说法不统一？
   - 有没有把模型组件名/接口名/文件名/端口/字节数/精度/函数名/代码变量名/硬件型号/安装步骤写进正文？能压成一句功能描述吗？
   - 有没有把代码里的变量名/函数名直接写进正文？能不能换成“输入的那句话/变成数字/逐个相乘相加”这类读者语言？
   - 同一个东西有没有两种叫法混用？有没有“代码里/程序里/实现里”这类工作痕迹？
6. 哪个 H2 只是标签？同一层有没有混维度？H2 有没有提前使用还没解释的结论/分数/阈值？读完它，我想不想继续读下一节？
7. 哪张图/caption 我看不懂它在说什么？它比文字多给了什么？
8. 对照 `reader_contract`：`can_skip` 有没有写进正文？`must_ground` 都落地了吗？每一节服务 `reader_goal` 吗？
9. 标题/H2 承诺的内容，正文兑现了吗？最后一个 H2 是不是“最后/总结/结语”？
10. 正文有没有把表格里的数字再逐个复述一遍？

只修最严重的 1–3 类问题；最多一轮；不要为了“更好”加事实、加情绪、加金句。

## 输出

- 开头：`<!-- reader_contract: {...} -->`
- 然后文章正文：`#` 标题；`##` 分节；需要时 `###`；列表、表格、图。
- 文末：`<!-- title_candidates: 候选一；候选二；候选三 -->`（用中文分号分隔，不要写成一行用 `/` 串起来）
- 不输出分析、自审、JSON、出处；出处由 runner 在正文外加。
