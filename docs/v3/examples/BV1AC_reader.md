# DeepSeek Harness 的四种模式，为什么不是四套程序

## 四种模式，不是四套程序

这期视频拆的是 DeepSeek Harness 这个开源框架，不是一次模型能力评测。先把它和“模型”“Agent 产品”分开，四种模式才不会看成一堆并列功能。它不是新模型，也不是已经打磨成熟的 Agent 产品，而是一个开源的 Agent 运行框架。所以它更像给开发者用的基础设施。

真正的问题不是“四种模式哪个更强”，而是：同一套框架凭什么能装出四种工作方式？

## 模型只负责想，Harness 负责让它能干活

基础大模型本身查不了外部实时信息：让它查一个 UP 主有多少粉丝，它办不到。外部程序可以执行工具，把结果回传给 AI；AI 再根据结果回答。

再往前走一步，模型负责思考和决策，工具由外部程序提供；不断重复思考、行动、观察，才变成能干活的 Agent。

Harness 管的是这套工程问题：工具、上下文、权限、校验、重试和运行记录。所以 Agent 是能干活的东西，Harness 是让它稳定干活的运行底座。

## Cordis 把“一切皆插件”变成可换的清单

DeepSeek Harness 的核心是 Cordis：一个独立开源的 TypeScript 插件框架，核心一句话是“一切皆插件”。插件可以理解为可按清单装拆的功能模块：这次装哪些，决定这个 Agent 有什么能力。

在 Harness 里，不只是工具；连模型适配器、文件系统、沙箱（隔离的运行环境）、会话日志，甚至 Agent 循环和 UI（界面）都可以是插件。所以除了 DeepSeek，其他主要大模型也可以接进来。

四种模式不是四套程序。它们加载的是四份不同的插件清单。换句话说，模式差异主要不在模型，而在这次装配了哪些能力、怎么调用工具、给 Agent 多大自主权。

## 四种模式，改的是装配方式

这四种模式，本质上是四种 Agent 组装方案。把四种模式放在一条链上看，它们分别动的是能力范围、工具调用协议和装配权。

标准模式是完整配置：文件编辑、网页搜索、Skills、计划、目标、子 Agent、工作流等能力都在，绝大多数情况默认选它。

PTC 保留标准模式的能力，但把模型调用工具的方式改了。标准模式让 AI 在一大堆工具里自由组合；PTC 则让 AI 写代码，由 Agent 框架执行代码来完成任务。中间工具的细节不必都交给大模型，能减少 AI 调用次数、节省上下文和 Token 费用，并更快；适合自动化程度高的任务。

极简模式砍的是装配量：系统提示词很短，只保留两个工具，没有 Skills、子 Agent、工作流，也没有上下文压缩。视频给它的定位是减少干预，没有进一步列出更细的适用清单。

创造模式改的是装配权：Agent 除了读文件、写代码、执行命令，还能查看 Harness 有哪些插件，把不同插件组合起来，创建新的运行模式。在作者的测试里，它被要求创建一个新模式，两轮后成功，并生成了一个专门搜 B 站数据的工具。同一条工作流，标准模式调用几十次大模型，这里只调用两次。

把四种变化压成一句话：标准给完整能力，PTC 改变工具调用，极简减少干预，创造让 Agent 组装新 Agent。

## 选模式，就是选让框架管到哪一步

把四种模式看成四份插件清单，选择就不再是“哪个模式更高级”，而是你愿意把哪些工程责任交给 Harness：保留完整能力让 Agent 自己组合，把编排写进代码减少来回调用，砍掉脚手架缩短链路，或者把装配权也交给 Agent。

这套解释能回答“为什么同一框架能装出四种模式”，但不能直接当成性能或安全结论：两次对几十次只是作者一次测试；PTC 脚本出错后的重试成本、每份插件清单的具体组成、插件权限和生态质量，都还需要自己验证。

作者也同意它现在难用、界面粗糙、配置复杂、文档对新手不友好，插件安全和生态质量没有经过时间检验。但官方定位是开发者预览版，面向想搭建、研究和改造 Agent Harness 的开发者，不是普通用户。用成熟产品的体验去要求它，比较对象就错了。

所以，四种模式共存不是功能堆叠，而是同一套插件能力按责任边界重新分配；选模式，本质是在选这项任务需要多少自动化、多少可控性。
