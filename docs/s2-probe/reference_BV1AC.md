## q1 central — 为什么同一套插件框架能组装四种模式

**Key points**

1. DeepSeek Harness 的真正核心是 Cordis：独立开源的 TypeScript 插件框架，核心理念“一切皆插件”。
2. 不只是工具，模型适配器、文件系统、沙箱、会话日志、Agent 循环乃至 UI 都可以是插件。
3. 四种模式不是四套程序，而是同一个 Harness 加载四份不同的插件清单。

**Evidence**：seg8-p01 521.9–542.1s；seg8-p02 542.4–555.0s。

**Scoring anchors**

- 2：三点齐全（Cordis/一切皆插件 + 插件覆盖多种能力 + 四份插件清单）。
- 1：只说“一切皆插件”但没有“四份插件清单/同一 Harness”，或只说“四种模式共享代码”但没解释插件化。
- 0：把四种模式说成四套独立程序；把 Harness 说成模型/产品本身；没有 Cordis。

## q2 mechanism — PTC 改变了什么，何时反而更贵

**Key points**

1. PTC = Programmatic tool calling；保留标准模式的能力，但改变模型调用工具的方式。
2. 模型写一段脚本，把 B、C、D 等工具串起来调用；Agent 只需调用三次大模型（而不是五次），中间细节不占上下文，因此更快、省 token。
3. 适合自动化程度高的任务。
4. 以上是理想情况；AI 写的脚本可能有问题或执行失败，要打回去反复修改，反而可能产生更多 AI 调用。

**Evidence**：seg6-p02 269.1–307.6s；seg6-p03 307.9–332.7s；seg7-p02 403.6–423.9s；seg7-p03 424.2–448.6s。

**Scoring anchors**

- 2：机制（写脚本串工具/改变调用方式）+ 收益（少调用/省上下文/token）+ caveat（脚本失败会反噬）。
- 1：只讲机制或只讲收益/caveat；把 PTC 说成“去掉模型”或“总是更快”。
- 0：说 PTC 与标准模式没有区别，或编造量化节省比例。

## q3 procedure — 标准 / 极简 / 创造三种模式的差异

**Key points**

1. **标准模式**：完整配置，文件编辑、Shell、网页搜索、Skills、计划、目标、子 Agent、工作流都有；绝大多数情况默认选它。
2. **极简模式**：系统提示词很短（一句话）；只保留两个工具（ASR 原文为“一个半型工具和一个文件操作的工具”；不要求评分者复述这个 ASR 词）；没有 Skills、子 Agent 工作流、上下文压缩；更依赖模型自身能力；适合做模型测试，观察最少干预下模型如何解决问题。
3. **创造模式**：Agent 可以查看 Harness 现有插件，把不同插件组合起来，创建一种新的运行模式（让 Agent 自己组装新的 Agent）；作者的测试中它创建了新工作模式和专用工具，搞了两轮才成功；新建会话可复用；同一任务标准模式要调用几十次 AI，新模式下只调用两次。

**Evidence**：seg6-p01 245.9–268.1s；seg6-p04 333.4–358.9s；seg6-p05 359.0–383.3s；seg7-p04 449.2–473.8s；seg7-p05 474.4–493.1s；seg7-p06 494.1–521.3s。

**Scoring anchors**

- 2：三种模式各有至少一个准确差异，且极简/创造的关键限制或效果正确。
- 1：覆盖两种模式；或三种都提到但有一处明显混淆（如把“创造模式”说成只是调用更多工具）。
- 0：只覆盖一种或全部混淆；编造视频没有的模式。

## q4 mechanism — 标准 vs PTC 的工作流/工具列表差异

**Key points**

1. 标准模式：请求里暴露一堆工具，Agent 在一大堆工具里自由组合完成任务。
2. PTC 模式：请求里只暴露一个工具 `runcode`（执行代码）；每一次 AI 请求调用的都是 runcode，只是执行的代码不同。
3. 也就是说，PTC 是让 AI 写代码、由 Agent 框架执行代码；标准模式是 AI 直接组合工具。

**Evidence**：seg7-p02 403.6–423.9s；seg7-p03 424.2–448.6s。

**Scoring anchors**

- 2：两侧差异都说对（标准多工具自由组合；PTC 只有 runcode/写代码执行）。
- 1：只说“PTC 工具更少”但没说明 runcode/写代码；或只说标准模式工具多。
- 0：说两种模式工具列表一样；编造工具名。

## q5 boundary — 有没有量化对比，边界是什么

**Key points**

1. **没有**四种模式在真实任务上的性能、成功率或 token 节省的量化对比。
2. 视频只给了一个单任务观察：标准模式“要调用几十次 AI 大模型”，作者创建的创造模式“只调用了两次”；创造模式“搞了两轮才成功”。这不是 benchmark。
3. PTC 也被明确说成理想情况，实际脚本可能失败、反而增加调用。
4. 明确的限制/未验证项（至少两点）：开发者预览版、不是成熟产品；安装需要 Node.js（有版本要求）、命令行启动、访问 localhost；界面粗糙、配置复杂、文档对新手不友好；插件安全和生态质量未经时间验证；面向开发者而非普通用户；普通用户可用 Codex/WorkBuddy 等消费级产品；不必 FOMO。

**Evidence**：seg6-p03 307.9–332.7s；seg7-p06 494.1–521.3s；seg9-p01 555.1–575.3s；seg10-p01 590.4–616.2s；seg10-p02 616.7–639.5s；seg10-p03 639.8–656.2s。

**Scoring anchors**

- 2：明确说“没有量化对比/不是 benchmark”，并给出至少两条视频明确说过的限制。
- 1：说了没有量化数据但边界笼统；或列了限制但没有指出“没有量化对比”。
- 0：把“几十次 vs 两次”当成模式间 benchmark；编造成功率/token 数字；宣称视频证明了某模式更好。
